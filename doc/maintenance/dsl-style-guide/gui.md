## Scripted Loc And GUI Text

Scripted loc is useful for displaying computed state, but GUI text controls do
not all behave the same.

Project conventions:

- Use scripted loc for compact state display such as enabled/disabled planet
  counts.
- When plain text controls fail to resolve variables reliably, use the verified
  `effectButtonType` display pattern.
- Display-only `effectButtonType` controls should visually behave like text and
  should not perform business effects.
- Keep value display localisation in GUI-specific keys, usually under
  `BCA_GLOBAL_SETTINGS_*`.

Known engine limits:

- `tooltipText` on GUI controls should be treated as static localisation. It
  has not been reliable for dynamic scripted loc such as `[From.some_loc]`.
- Use button-effect `custom_tooltip` for player-facing dynamic tooltip text.
- A button effect should use only one `custom_tooltip` for the visible tooltip.
  Multiple or conditionally emitted `custom_tooltip` blocks in the same effect
  are unreliable.
- When a tooltip must vary by state, point that single `custom_tooltip` at a
  localisation key that calls scripted loc, and let the scripted loc select the
  final text.
- For conditional tooltips, prefer putting `custom_tooltip` at the outer effect
  level and the condition inside the tooltip block. Do not hide tooltip
  creation inside an `if` branch unless the exact pattern has been tested in
  game.

Example pattern:

```text
effect = {
    custom_tooltip = BCA_SUPPORT_DISPLAY_TOOLTIP
    hidden_effect = { ... }
}
```

```yaml
BCA_SUPPORT_DISPLAY_TOOLTIP: "[From.bca_support_display_tooltip]"
```

## Tooltips And Hidden Effects

Player-facing button effects should not expose raw implementation details.

Rules:

- Use `custom_tooltip` for the text players should see.
- Put implementation effects inside `hidden_effect` when raw effect output
  should not be shown.
- Buttons that need tooltips should not be made fully click-through or always
  transparent. In particular, verify `alwaysTransparent` behavior when using an
  icon-only or display-like button as a tooltip host.
- For one-shot bulk actions, do not style buttons as persistent state toggles.
- For selected/default state buttons, make the highlighted state match the text
  shown on the button.

## Event GUI Rules

Custom event GUI is fragile because the engine expects several vanilla
event-window fields.

Rules:

- Keep required shell fields centralized in
  `mod_builder/templates/component/event_gui_shell.j2`.
- Keep business controls in content/component templates.
- Do not copy hidden/displaced vanilla event fields into business GUI
  templates.
- If an event GUI opens blank, loses close behavior, or crashes surrounding UI,
  inspect the shell first.
- Event GUI scope should be stabilized with event targets when controls read
  country-level state.

## External Panels And Clipping

Custom support/side panels may need to extend outside the visual content area.
The current event GUI shell relies on `clipping = no` at the top-level
`containerWindowType` for that behavior.

Rules:

- Do not solve external-panel clipping by duplicating or relocating shell
  compatibility fields into business templates.
- Keep hidden compatibility widgets far outside the visible area, currently
  around `x = -10000` and `y = -10000`.
- If an external panel disappears at the parent boundary, inspect shell
  clipping before changing panel coordinates.

## Text Icons And Image-Like Buttons

GUI text icons are not scalable in the same way as normal textures.

Rules:

- Do not rely on GUI scale to resize a text icon image.
- Generate DDS assets at the size the GUI needs.
- Keep GUI layout size and generated DDS size in sync through shared config
  when possible.

## Support Panel Assets

Support panel images are generated by `mod_builder/image_gen.py` from source
assets under `mod_builder/assets/bca_support/`.

Rules:

- Replace source PNG assets first, then regenerate DDS assets.
- Reaction/expression assets currently default to direct resize and DDS output;
  `support_image_style.reaction_postprocess` is `false`.
- QR code assets may use their own formatting path, because scan readability
  matters more than matching expression-image styling.
- Shared support panel size and image style values live in
  `mod_builder/templates/generated_configs/support_layout.yaml`, which is a
  documented handwritten exception in the generated-config directory.

## Link Buttons

`web_link` exists in button-like GUI definitions, but it did not work in the
support panel button test. Do not depend on `web_link` for an external support
entry unless a future in-game test proves the exact control and context work.
